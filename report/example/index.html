1. Executive Summary

We assessed the self-owned OWASP Juice Shop lab application on October 27, 2026. We confirmed eight weaknesses: three critical, three high, one medium, and one low. The most urgent problem is that an outsider can reach customer information and administrator functions without a valid account.

An outsider can sign in as an administrator without a password. A separate flaw in product search could also expose records held in the database, and a key published with the app lets an outsider pose as an administrator. These paths put customer data, store controls, and trust in the business at risk.

Fix the three critical weaknesses immediately, starting with the search and sign-in flaws, then replace the exposed key used for sign-ins (see §6). The application did correctly deny access to one sensitive route. We will retest repaired findings at no charge within 30 days, as described in §7.

2. Scope & Methodology

In-scope assets: http://127.0.0.1:3000 (OWASP Juice Shop v20.3.0, Docker, loopback-only binding) — per ROE §2.

Out of scope: DoS testing, social engineering, physical testing, host services other than port 3000 (ROE §5).

Test window: 2026-10-27.

Methodology: Reconnaissance (nmap 7.98 full-port), automated signature scanning (nuclei v3.11.1, 4,374 templates, rate-limited 50 req/s, 10 concurrent — 0 CVE-signature matches), AI-assisted logic-flaw analysis with human verification of every finding (exact curl reproductions, response inspection), and root-cause confirmation against the running container's source. ~30 rate-limited, read-only probes total. State changes were limited to: (a) creation of one designated low-privilege test account required for the BOLA proof, and (b) a product-price change with immediate restoration (F-06), performed to demonstrate the unauthorized write and return the system to its prior state.

Limitations: Single test window; no source code review beyond routes implicated by findings; frontend bundle secrets sweep covered shipped artifacts only; no authenticated-admin deep enumeration (out of ROE technique list).

4. Detailed Findings

F-01 — Unauthenticated SQL injection in product search (full database read) — CRITICAL 9.8

Location: GET /rest/products/search?q=

Description: The search parameter is concatenated directly into a SQLite LIKE clause. An attacker closes the query and appends a UNION SELECT, controlling the full result set.

Business impact: An attacker with no account can reach data beyond product listings, potentially exposing customer records and creating breach-response and notification costs.

Evidence: F-01-sqli.txt — 57-row JSON response containing an injected row (sqlite_version()); raw SQLITE_ERROR pages on malformed input confirm string concatenation.

Reproduction:

curl -s --get --data-urlencode \
  "q=')) UNION SELECT sqlite_version(),'1','2','3','4','5','6','7','8','9'--" \
  "http://127.0.0.1:3000/rest/products/search"

Remediation: Replace string concatenation with a parameterized query or Sequelize literal-bound replacements.

References: CWE-89 · OWASP A03:2021

F-02 — SQL injection authentication bypass (admin login without password) — CRITICAL 9.8

Location: POST /rest/user/login

Description: The login lookup interpolates the email field into SQL. ' or 1=1-- in the email matches the first user row (id 1 = admin) and returns a valid admin session token.

Business impact: An attacker with no account can sign in as an administrator without knowing a password, gaining control over privileged functions and putting customer data and store operations at risk.

Evidence: F-02-loginbypass.txt — HTTP 200 with an authentication.token decoding to {"id":1,"email":"admin@juice-sh.op","role":"admin"}.

Reproduction:

curl -s -X POST -H 'Content-Type: application/json' \
  --data-binary '{"email":"'"'"' or 1=1--@juice-sh.op","password":"x"}' \
  "http://127.0.0.1:3000/rest/user/login"

Remediation: Exact-match credential lookup via the ORM plus bcrypt verification; never interpolate user input into SQL.

References: CWE-89 · OWASP A07:2021

F-03 — JWT forgery via hardcoded RSA private key — CRITICAL 9.1

Location: JWT verification for all authenticated endpoints; key material in lib/insecurity.ts / encryptionkeys/jwt.pub

Description: The application ships a hardcoded RSA private key whose modulus is identical to the deployed public key. Anyone with the public source can mint arbitrary admin tokens.

Business impact: An attacker with access to the public application source can create a valid administrator identity, exposing customer records and creating breach and compliance risk.

Evidence: F-03-jwtforgery.txt — modulus SHA-256 match between deployed jwt.pub and source key; forged-token request returning admin data.

Reproduction: Extract key from source → sign payload {"data":{"id":1,"role":"admin",...}} RS256 → request /api/Users with the forged token.

Remediation: Generate keys per deployment at install time; load the private key from a protected runtime secret; rotate the deployed pair.

References: CWE-321 · OWASP A02:2021

F-04 — BOLA: any authenticated user reads any user's basket — HIGH 8.6

Location: GET /rest/basket/:id

Description: Basket lookup is driven purely by the path ID; no ownership check ties the requested basket to the token's user id.

Business impact: A customer with a free account can read another customer's basket, exposing purchase choices and quantities and undermining privacy and trust.

Evidence: F-04-bola.txt — register low-priv user → login token (role customer) → GET /rest/basket/1 returned admin's basket.

Remediation: Derive the basket server-side from the verified token; reject cross-user IDs.

References: CWE-639 · OWASP A01:2021

F-05 — Password hash embedded in every issued JWT — HIGH 8.1

Location: POST /rest/user/login response token payload

Description: Every issued token carries the user's password claim — verified as the unsalted MD5 of the plaintext password.

Business impact: An attacker who obtains a customer's sign-in token can use the password data inside it to try to recover that password, increasing account-takeover risk wherever it was reused.

Evidence: F-05-jwthash.txt — decoded token payload.

Remediation: Strip password/totpSecret claims from token payloads; hash with bcrypt/argon2; return only id/email/role.

References: CWE-522 · OWASP A04:2021

F-06 — Unauthenticated product price manipulation — HIGH 7.5

Location: PUT /api/Products/:id

Description: The admin guard on the update route is commented out, so the request falls through to the generic unauthenticated CRUD layer.

Business impact: A visitor without an account can change a product's listed price, putting sales revenue and the integrity of the storefront at risk.

Evidence: F-06-price.txt — unauthenticated PUT succeeded; guard verified absent in source.

Remediation: Restore the authorization middleware on all write routes; default-deny the generic CRUD layer for non-admin roles.

References: CWE-862 · OWASP A01:2021

F-07 — Security-question enumeration oracle — MEDIUM 5.3

Location: GET /rest/user/security-question?email=

Description: The response differentiates known vs unknown emails ({"question":{...}} vs {}), enabling account enumeration and reset-flow recon.

Business impact: Someone who knows or guesses an email can confirm whether it has an account and see its security question, making targeted phishing and account attacks easier.

Evidence: F-07-enum.txt.

Remediation: Return a uniform response for known/unknown emails; rate-limit the endpoint.

References: CWE-204 · OWASP A07:2021

F-08 — Verbose error pages exposing stack traces and SQL errors — LOW 3.1

Location: Global error handler (malformed search query; 401 pages with server banner)

Description: Raw SQLITE_ERROR bodies and Express stack-trace HTML are returned to clients, leaking framework versions and query structure.

Business impact: A visitor who triggers a malformed request can see database and server details, making attacks easier to plan when combined with other flaws.

Evidence: F-08-errors.txt — HTTP 500 HTML page titled Error: SQLITE_ERROR: near ")": syntax error.

Remediation: Generic error responses; log details server-side only.

References: CWE-209 · OWASP A05:2021

5. Positive Observations

  • During testing, the application rejected a token claiming no signing method, which blocked that attempted sign-in bypass.
  • A sweep of the shipped frontend files found no embedded secrets in the reviewed files.
  • The security-answers route denied the tested request, blocking the suspected cross-user access path.

Appendix B — Glossary

  • SQL injection: a flaw that lets supplied input change a database command.
  • IDOR/BOLA: a missing ownership check that lets a user access another user's record.
  • JWT: a signed credential the application uses to identify a signed-in user; security depends on protecting the signing key and limiting the data inside it.
  • CVSS: a standardized technical severity score used to prioritize findings, not an estimate of financial loss.
  • Parameterized query: a query that treats supplied input as data rather than part of the command.
